# 纸上赶稿｜P1 催稿节点与返修逻辑 v0.1

> 2026-11-15；对应网页 [v0.5-alpha](../../projects/fandom-ddl-calendar/v0.5-alpha/README.md)。该版本为测试版，未完成全量端到端验收。

## 一、产品边界

仅主催操作。外部作者和画师不登录，也不需要填每日字数和用时。「主催」日历处理交稿节点、催稿提醒、待验收与返修；「我的」日历继续处理主催自己每天的进度；「全部」只显示制品收货 DDL。不包含经营/库存功能。

## 二、分离两种事实

**联系事实**记录何时提醒、联系了哪一个交稿目标；已联系不代表交稿。

**交付事实**记录收到稿件、待验收、请求修改、最终确认以及真实日期；不能因用户修改约定日期而抹掉历史事件。

建议在 `Step` 上维护：
- `contactHistory[]`：`id,date,targetKey,targetDate,note`；
- `deliveryHistory[]`：`id,type,date,note,previous`；
- `deliveryStatus`：`pending | submitted | revision | accepted`；
- `revisions[]`：`id,requestedAt,dueDate,note`；用于同一份稿件尚未验收时的返修轮次。

旧版只保存 `completed=true` 的工序仍可视为已完成，但 **`completedAt=null` 必须保留未知，不可补写今天**。

## 三、交稿与验收状态

| 状态 | 中文 | 排程含义 |
|---|---|---|
| `pending` | 等待交稿 | 交稿节点仍未满足 |
| `submitted` | 已提交待验收 | 有稿件提交记录；不等于最终验收完成 |
| `revision` | 需修改 | 原承诺交稿日保留，新返修目标日期单独记录 |
| `accepted` | 已确认完成 | 完成前置条件；保留实际确认日期与提交历史 |

直接将已验收内容切换回「需修改」会丢失原完成事实，因此当前实现要求使用「追加返修」。

- **未验收时追加返修**：当前工序仍未完成；增加一轮返修记录，最新返修约定日期用于预测，而原始承诺日保留。
- **已验收后追加返修**：在原工序之后插入新的独立返修工序，原验收记录和实际日期保持不变。新工序进入正常依赖链，可能造成后续生产日期风险。

## 四、提醒和待处理区

- 默认提前 7 天，用户可调整；设置 0 关闭提前提醒。
- 基础提醒开始日 = 当前交稿目标日 − 提前天数；返修轮次有独立目标。
- 联系记录包含 `targetKey = 返修轮次 | 交稿日`，因此同一轮已经联系后不会重复提醒，但改期或产生新的返修轮次可再次提示。
- 未联系提醒跨天持续显示；交稿日当天显示「今日交稿」；超过交稿日仍未验收显示「交付逾期」，**即使已经联系过也继续显示逾期**。
- 已提交但未验收显示「待验收」。
- 「主催」视图顶部的「需要处理」区最多默认展开四项，可手动展开其余，月历仍是简洁节点标记。
- 当前只有网页内提醒，不会自动向其他参与者发送消息或推送手机通知。

## 五、日期与历史规则

- `promisedDelivery`：原始人工约定，不被返修覆盖。
- `revisions[].dueDate`：新一轮返修交稿目标。P0 桥接层会在复制后的计算输入中优先使用它；**原始数据不被覆盖**。
- `latestAllowedFinish`：从最终收货 DDL 倒推的最晚允许完成日。
- `actualFinished`：用户明确记录的真实验收日期；缺失时未知。
- `baseline`：首次确认的原计划日期；状态变化不写回旧基线。

- 18 项 P1 独立状态测试通过；
- 33 项 P0 引擎测试和 12 项 P0 桥接测试通过；
- Chromium 实际交互检验通过：联系 → 提交待验收 → 返修 → 验收 → 已验收后再追加返修；
- v0.4 JSON 导入测试通过，原定计划及未知完成日期保留。

这些覆盖核心链路，并不等于所有异常和误录撤销已经验证。
