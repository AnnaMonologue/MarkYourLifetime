# 纸上赶稿｜排程引擎技术研究 v0.1

> 日期：2026-11-15  
> 状态：**技术研究与 P0 验证方案，尚未接入正式网页**  
> 上游需求：[产品逻辑总规范 v1.0](PRODUCT_LOGIC_v1.0.md)  
> 范围：只研究 DDL、阶段依赖、约定交稿、实际完成、重新排期、催稿提醒和进度一致性；不增加销售/库存/经营功能。

## 1. 研究结论

建议**替换 v0.3.1 目前单函数即时倒排的做法**，分为：

1. 输入与历史层：收货硬性 DDL、人工约定、工序依赖、预计工期、实际完成事件；保留原定计划快照。
2. **逆向计算**：从收货 DDL 倒推各环节「最晚允许开始/完成日」，即不可晚于哪天，**不看已完成状态来删环节**。
3. **正向预测**：从今天、实际完成日和外部承诺交稿日，计算未完成环节的「预计完成日」。
4. **冲突与风险**：比较预计完成与最晚允许日期，列出差距；已发生历史不改写，人工约定日期不自动调整。
5. **日历投影**：以上结果分别映射为「全部 / 主催 / 我的」；日历不再自己重新计算业务规则。

这可以避免当前已完成运输后，生产工期被推进到签收当天，以及每天打开日历原计划自动漂移的问题。

## 2. 已检查的旧版实现问题

审阅对象：本地 v0.3.1 HTML 中的 scheduleProduct()、allCalendarEntries()、stepDone()、save-log 等。

| 代码机制 | 发现 | 处理原则 |
|---|---|---|
| 倒排时遇到 doneStep 即跳过 | 已完成工序从依赖链消失，前序工序会占用原本属于运输/生产的时间 | 完成是状态事实，依赖图始终保留 |
| scheduleProduct(now=todayISO()) | 实时今天参与所有计划分配，缺少存储的原计划 | 原定快照不变；只更新未来预测 |
| 运输只靠最后一个 shared 工序 + 名称识别 | 特殊处理脆弱，缓冲天数隐藏在 -2 计算中 | 运输是单独的物流参数和寄出/收货里程碑 |
| 节点日仅由估计工期推算 | 无法表达画师承诺交稿日期、印厂已确认的收稿日 | 单独保留承诺日/指定上限与计算结果 |
| 提醒仅为单日黄色条目 | 过日历日期后不再是持续待处理事项 | 提醒日期和催稿处理状态分开 |
| 图稿 pieces 布尔值和 logs 同时记录 | 部分更改/删除日志可能造成不同步 | 明确唯一进度来源并派生各页/张的状态 |
| isMine / fixed / external 逻辑交织 | 任务是否属于本人、是否有数量目标和是否等待交付是不同维度 | 拆分负责人归属、工序类型和状态 |

## 3. 日期的精确定义（P0 的前提）

第一版统一采用**用户本地自然日**，而非毫秒除以 86400000。不得默认某日期自动减 1，因为用户在活动创建时已经手填建议的收货 DDL。

- **收货 DDL（receiptDeadline）**：主催输入，视为该日结束前必须签收的硬性上限。
- **物流提前量（transitDays）**：寄出与预计签收之间的自然日差值；默认值待决定，可编辑。
- **最晚寄出（latestDispatch）** = 收货 DDL − 物流提前量。
- **寄出前缓冲（handoffBufferDays）**：大货完成到寄出之间至少留出的日数；用户可设 0/1/2……，不可在代码里隐含。
- **最晚生产完成（latestProductReady）** = 最晚寄出 − 寄出前缓冲。
- **持续 d 天的实体工序**（d ≥ 1）若最晚完成于 E，其最晚开始日 = E − (d−1) 天；默认下一道工序最早次日开始。
- **即刻发生的里程碑**（寄出、签收、人工交稿）没有「工期 1 天」的含义，应独立于生产步骤。

**算例（自然日、提前量 3、缓冲 1）：**

| 项目 | 日期 |
|---|---|
| 收货 DDL | 2026-12-30 |
| 最晚寄出 | 2026-12-27 |
| 大货最晚结束 | 2026-12-26 |
| 大货预计用 7 天 | 最晚 2026-12-20 开始 |

在「全部」日历中仅显示收货 DDL；在「主催」日历中显示生产节点、最晚寄出及收货 DDL，不在签收日再生成一条同义的「运输完成」节点。

**待用户确认**：运输是否同时需要工作日算法、揽件时间、官仓/酒店明确签收时段；V1 可以保留自然日，但必须允许填写足够的提前量和缓冲。

## 4. 不同性质的日期分别存储

| 字段建议 | 含义 | 自动重算？ |
|---|---|---|
| receiptDeadline | 收货硬性截止日 | 否；主催手动更改并保留历史 |
| dueBy | 工序必须不晚于的人工硬约束（如印厂收文件） | 否 |
| promisedDelivery | 外部人员承诺的预计交稿日期 | 否；不能替画师自动改期 |
| latestAllowedFinish | 按 DDL 和后续依赖倒推的最晚允许完成日 | 是 |
| forecastFinish | 从当前剩余工期、前置完成记录和承诺日期推算的完成日 | 是 |
| actualFinished | 经主催确认的真实完成日 | 否 |
| baselineFinish | 首次确认计划时保存的原定日期 | 否 |

**不能把 promisedDelivery 直接当作 latestAllowedFinish。** 如果画师承诺 12/24 交稿，而下印要求 12/19 前完成，两者应同时展示并报告「晚于要求 5 天」；程序不能虚构画师会提前交稿。

已承诺日期过去但没交，系统应提示「承诺已逾期，需确认新的交付预期」，不可将逾期的日期当成真实完成记录。

## 5. 用依赖图（DAG）而非把所有步骤串起来

工作内容仍使用主催易懂的模板列表；内部用稳定 ID 和前置依赖构建有向无环图。下印前的合并点需要**等待所有必要路线都完成**。

示例：

~~~
作者 A：正文 → 校对 ─┐
                      ├→ 文件齐备 → 打样 → 样品确认 → 大货
画师 B：封面 → 美工 ─┘
                                  ↓
                           寄出 → 运输 → 收货 DDL
~~~

每条路线内部默认串行，但不同路线可并行。特定依赖要明确；不能因为 UI 中谁排在上面，就假定全部工作必须依次完成。图中如有环（A 等 B，B 又等 A）应拒绝生成计划并指出冲突。

## 6. 两遍排程伪算法

**第一遍：倒推允许的最晚日期**（与 completed 无关）。

~~~text
latestDispatch = receiptDeadline - transitDays
latestProductReady = latestDispatch - handoffBufferDays

for step in reverseTopologicalOrder:
  if step has no downstream step:
     latestFinish = latestProductReady
  else:
     latestFinish = min(child.latestStart - 1 day)

  if step.dueBy exists:
     latestFinish = min(latestFinish, step.dueBy)

  latestStart = latestFinish - (step.durationDays - 1 day)

  if step.promisedDelivery > latestFinish:
     emit conflict (promisedDelivery - latestFinish)
~~~

**第二遍：根据实际记录进行正向预测**。

~~~text
for step in topologicalOrder:
  if step is confirmed completed:
     forecastFinish = step.actualFinished
     if actualFinished missing: mark UNKNOWN; request backfill
  else:
     earliestStart = max(today, all predecessor forecastFinish + 1 day)
     forecastFinish = earliestStart + remainingDuration - 1 day

     if step is external and promisedDelivery >= today:
        forecastFinish = max(forecastFinish, promisedDelivery)

     if promisedDelivery < today and unfinished:
        mark overdue promise; do not assert a known ETA

  if forecastFinish > latestAllowedFinish:
     emit predicted lateness with day difference
~~~

注意：上述正向值是按现有工期与日期推算的**最早合理估计**，不是物流保证，也不是画师一定按时交稿的保证。若完成历史缺日期，绝不凭当前日期伪造实际日期。

**状态不应隐式改变依赖：**确认打样完成后，打样仍是大货的前置条件；仅在正向预测中使用打样实际完成日。确认已寄出后，仍保留最晚寄出及生产完成的历史约束。若已寄出但大货尚未标完成，应提示数据矛盾，不自行将大货视为已完成。

## 7. 两个不同的「计划」

1. **基线计划**：主催第一次确认排期时写入 snapshotId、时间、输入版本、每个节点原定日期，绝不因为打开页面或标记完成而重写。
2. **当前预测**：随剩余工作量、人工输入和当前日期变化。重新生成仅限未完成的未来任务。日历详情允许对比「原计划 / 最新预计 / 实际」。

用户修改活动 DDL、阶段顺序、工期或目标数量后，保留原基线；新规则生成新的方案版本，并标注受影响节点。仅浏览页面不应改变任何存档数据。

## 8. 我的每日进度（数量守恒）

- 仅主催负责的任务做逐日分配，外部画师、作者只管理交稿节点。
- 剩余量 = 当前目标量 − 初始有效完成量 − **已确认且未撤销**的日志新增量；绝不把「少写的 900 字」再创建一份独立任务加一次。
- 按剩余可用日期分配整数字数、整数张数；如允许 0.5P，用「半 P」为最小整数单位进行计算，最后转换展示。
- 通过累计份额取整，确保每天之和恰好等于总剩余量，允许某些日为 0。
- 主催点击「我的」任务卡只需录入**日期、今日进度、今日用时（选填）、标记完成**，没有计时器。
- 跨制品统一汇总到「我的」：如果没有个人产能或单位耗时输入，展示多任务总览但不声称「当天一定做得完」；有数据才进一步提示负荷风险。
- 对 P 数/画稿阶段采用稳定的作品 ID 和阶段完成事件；不要让「逐张勾选」和「新增数量日志」双重计数。删除/更正日志后应由唯一有效记录重建状态。
- 文本应区分「今日新写字数」「当前成稿净字数」与「返修」。改稿、删字可能减少成稿量，不能让单一的累计新增量等于当前成稿量。

## 9. 主催催稿与提醒

- 外部交付节点至少有：目标日期、约定日期（如存在）、实际提交/验收日期、状态。
- 提醒开始日期 = 对应有效交稿节点日期 − 用户设置的提前天数；默认 7 天、0 表示关闭。
- 「是否已催过」与「是否已交稿」是独立状态；催过不等于完成。
- 黄色提醒在触发后若尚未处理，应持续进入主催待办区；不是错过当天就彻底消失。
- 提醒被确认处理后，主催仍能查看尚未交付的蓝色节点，届期未完成再显示逾期。
- 本阶段仅网页内提醒，不承诺推送通知。

## 10. 数据模型与迁移建议

建议的最小实体：

| 实体 | 关键字段 |
|---|---|
| Event | id、名称、模式、收货 DDL、时区 |
| Product | id、类型、活动 ID、制品名称、运输提前量、交接缓冲 |
| Step | id、前置 stepIds、负责人标签、isMine、工序类型、目标量/剩余工期、promisedDelivery、dueBy |
| ProgressEvent | id、stepId、事件日期、计入数量/净量/阶段、用时、变更类型、记录时间 |
| ActualMilestone | id、stepId/寄出/签收、实际日期、提交/验收状态 |
| ScheduleBaseline | id、inputVersion、创建时间、不可变原定节点日期 |
| ReminderState | 节点 ID、提前天数、是否已联系、处理时间、交付状态 |

旧 JSON 不得直接覆盖为新结构；应先检查、备份、迁移、校验。特别是旧 completed=true 却没有 completedAt 时，实际日期应标 UNKNOWN；不能填今天。已经录入的图稿 piece 状态要保留并核对日志去重。迁移失败则回滚而不是丢失记录。

## 11. 独立验证实验

已编写**未接入网页的 Python 参考原型**，仅使用标准库。按上述日期边界、DAG、历史实际日期、承诺日期及数量守恒规则完成 **17/17 项自动测试**：

| 覆盖点 | 结论 |
|---|---|
| 收货 12/30、物流 3 天、缓冲 1 天、大货 7 天 | 最晚寄出 12/27；大货 12/20–26 |
| 标记已寄出且大货实际 12/26 完成 | 不会把大货截止日移到收货日 |
| 已完成下游工序 | 不删除此前工序的截止关系 |
| 仅改变今天日期而未修改 DDL | 最晚允许日期保持不变 |
| 正文与封面并行后汇合 | 两路分别计算，文件汇合依赖两路完成 |
| 封面最晚 12/19，承诺 12/24 | 报告承诺交付比必要时间晚 5 天 |
| 12/25 才开始 7 天大货，最晚 12/26 完成 | 预测 12/31 完成，报告晚 5 天 |
| 旧版已完成但实际日期缺失 | 标记未知并提示补录 |
| 数量任务分摊 21,900 字至 7 天 | 每日配额之和仍是 21,900 |
| 寄出比最晚寄出日晚 2 天 | 收货 DDL 不移动，提示超期 |
| 外部承诺日过期 | 显示失约提示 |
| 存在环形依赖 | 拒绝排程 |
| 下游已完成但上游未完成 | 提示历史矛盾 |
| 人工指定较早的工序截止日 | 正确向上游传播 |
| 用户修改收货日期 | 重新计算但原始输入未被隐式改写 |
| 零日物流/零日缓冲 | 日期边界一致 |
| 实际完成晚于最晚日期 | 标记历史逾期 |

**实验边界**：这 17 项是纯 P0 算法测试，**不等于**原产品规范中 15 项端到端验收全部通过。尚未测试：五类模板完整迁移、逐页/逐张阶段追踪、跨制品产能、催稿持久化状态、旧数据导入、网页集成。

## 12. 实际实施顺序（建议）

1. **先冻结 v0.3.1**：备份 HTML 与真实 JSON，禁止原地覆盖；新排程算法先作为独立可测试模块。
2. **P0a 数据分离**：硬性日期、人工约定、实际日期、唯一进度源、基线计划明确分离；运输转为显式物流提前量。
3. **P0b 排程引擎**：拓扑排序、双向日期计算、诊断风险；先用固定案例通过自动测试。
4. **P0c 接入**：在新版本中将日历从计算器变成纯结果呈现；保证「全部 / 主催 / 我的」互不混乱。
5. **P0d 数据迁移**：旧数据只迁移能证明的信息，不猜历史；整包备份并允许恢复。
6. **P1 功能核验**：承诺节点、持续催稿、逐张进度、每日产出与跨制品负担，再进行 15 项端到端验收。

### 尚需决定（不阻断 P0 算法原型）

- 默认运输与缓冲的具体数字、是否使用工作日/自然日。
- 印厂已开工但尚未完成时，剩余工期由主催估算，还是保留原始工期；建议让主催更新「剩余预计天数」，不能根据已过去几天机械扣减。
- 计划基线是在首次创建制品时自动生成，还是首次点击「确认排程」时保存；建议确认排程后固定。
- 外部节点返修是否追加独立工序；建议保留原验收记录并追加返修，不直接把原完成历史删除。

**结论**：先正确表达日期和依赖，再考虑页面展示。日历应展示已计算好的截止日、提醒和每日任务，而不是决定任何工序的日期。
