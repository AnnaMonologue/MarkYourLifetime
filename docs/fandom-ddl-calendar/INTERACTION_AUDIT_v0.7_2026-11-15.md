# 纸上赶稿｜v0.7 Alpha 全交互与交叉流程审计报告

> 审计日期：2026-11-15（Asia/Singapore）  
> 对象：`projects/fandom-ddl-calendar/v0.7-alpha/index.html` 对应的本地 v0.7 发布 HTML；审计时**没有修改被测网页**  
> 审计级别：**代码静态梳理 + Chromium/Playwright 动态操作 + P0/P1 既有测试回归**  
> 性质：这是**验证报告**，不是已经修复问题的新版本；所有“通过”仅代表所列场景的预期行为通过，不代表任意组合都经过形式化穷举。

## 1. 最终判断

**v0.7 的基础操作能够运行，但尚不具备“所有交互及交叉场景都运行顺利”的验收条件。**

- 新增的**54 项独立交互/交叉测试**：**42 项符合预期、12 项未达到预期**。其中部分是功能错误，部分是业务约束未落实或缺少交互反馈；**12 项不代表 12 次 JavaScript 崩溃**。
- v0.7 自带的 `test_v07.py`、`test_calendar_deep.py`：两组均通过，覆盖桌面和手机的基础筛选及点击。
- 先前的纯算法单元测试重跑：P0 33/33，通过；P0 桥接 12/12，通过；P1 催稿状态 18/18，通过。**这说明算法基础单例能工作，不等于网页端的状态联动正确**。
- 静态入口梳理：源码中发现 **61 个 `data-action` 分发分支**；60 个有模板里的事件入口，`select-day` 是目前没有可见入口的遗留分支。按正则统计源码有 81 个命名函数（包含封装的算法模块及页面逻辑）。**不能把 61 个入口误写成 61 项已经实际点测通过。**
- 大规模简单压力情景：1、3、5、10 件“各含 60 位参与者的合志”可计算和渲染；**单次**实测计算约 29–81 毫秒、渲染约 14–69 毫秒（当前测试机/Chromium，仅用于粗略基准，不代表手机稳定性能，也未测试数千条日志后的长期使用）。

最需要先解决的：**过期未完成任务在“我的进度”消失、逐张画稿与日志冲突、无效物流排序使整件制品排程失效**。在这几项修复前，不能把 v0.7 宣称为可靠的正式赶稿排程工具。

## 2. 真实产品边界（必须保持）

本项目是一名主催**自己记录、自己提醒、自己处理**的工具。画师/作者不需登录。已明确排除自动发送催稿信息、短信/邮件/推送、多用户协作、旧版本迁移、销售库存与财务经营、计时器。保留当前版本 JSON 导出，但**当前没有任何导入/恢复入口**：这份文件只能用作数据留档，不能直接恢复到网页。以后如讨论“同版本备份恢复”，必须明确区别于用户已拒绝的“旧版迁移”，不能擅自新增。

## 3. 全部主要对象及写入关系

```text
活动 Event （名称、官仓/酒店、手填收货 DDL）
  └─ 关联多个制品 Product（五模板、名称、寄出前缓冲、原计划快照）
      ├─ 内容路线 Track A → 工序 Step 1 → Step 2 → ...
      ├─ 内容路线 Track B → 工序 Step 1 → Step 2 → ...
      ├─ 图稿 Piece（某张图草稿/上色/细化完成标记）
      └─ 下印工序 Shared Steps → 最晚寄出 → 收货 DDL
              ↑              ↑
        个人进度日志 Logs   外部催稿/交稿/验收/返修记录
              └──────────────┘
                  ↓ 触发重新计算
           P0：倒排允许最晚日期＋正向预计日期
           P1：联系状态、提醒起始日期、交付状态
                  ↓ 日历投影和每日安排
              ┌──────────┴──────────┐
           赶稿日历                 我的进度
       全部／主催／我的          今日工作／需要关注／未来14天／最近进度
```

写入类型应严格区分：用户手动 DDL/承诺日期（事实约束）；`completedAt`、`logs`（实际发生）；`baseline`（冻结计划）；`forecast`、每日配额（计算结果）；联系历史和交稿历史（备忘事件）。当前实现部分场景没有做到完全分离。

| 多制品 → 同一天多项任务 → 三日历筛选 → 日期弹窗 | 不改动底层数据，统计随筛选变化 | **通过** |

## 6. 未达预期项的逐条定位与修复优先级

### P0：直接影响赶稿安排或数据一致性

**X01：逾期任务在“我的进度”消失。**
- 复现：创建小说本，收货 DDL 改成距今 1 天；个人路线仍有 3 个未完成环节，系统出现延期诊断，但 `personalTodayRows(todayISO())` 返回 0。
- 根因：`scheduleProduct()` 个人卡片生成以倒排的 `row.latestFinish` 为终点；`begin > end` 时不产生任何当天任务。`myProgressPage()` 只读取这些卡片。
- 方案：将“仍未完成的个人任务列表”与“某一天的有效计划配额”分离。过期任务始终进入“我的进度”的 **逾期待做**，展示剩余量、原截止、当前预计、风险；对于确实已无可分配日期的任务，不捏造当天配额，可显示“需重新安排”。

**X03：画稿手动确认与日志回滚互相覆盖。**
- 真实点击复现：在图集内记 1 张草稿 → 该画稿打勾 → 手动取消并重新勾选 → 删除原日志，结果人工最终确认被置为未完成。
- 根因：`piece.sketch/color/refine` 布尔值既由日志写入，也由手动按钮直接切换；删除日志无条件将 `pieceIds` 对应布尔位设为 `false`。
- 方案：每张图每阶段保留唯一权威的**阶段事件记录**（来源、日期、变更 ID），界面状态从有效事件推导；撤销某日志只能撤销该日志的效力，不清除其后的手动确认。

**X07：逐张画稿“完成”缺少日期，后续预测受阻。**
- 复现：图集 2 张都手动勾“草稿完成”；`doneStep=true`，但 `actualFinished=null`，算法报告“已完成但缺少实际完成日”；之后上色、细化、生产的正向预测可被阻断。
- 根因：逐张勾选只写布尔值，不写阶段实际日期；P0 正确拒绝猜测日期，但界面没有同步采集该事实。
- 方案：手动勾选阶段时以**当前日期**为默认、允许修改；历史已有布尔但缺日期要标“日期未知”并提示补录，不反填今天。

**X08：运输重排导致整件制品排程不可用。**
- 复现：制品 → 下印环节 → 管理流程 → 将“运输”上移到“大货”之前。
- 根因：按钮允许任意排序，P0 适配器要求物流工序恰好一条且位于下印列表末尾；`scheduleProduct()` 捕获异常并返回空排程、风险文字。
- 方案：前端禁止把运输放到非末位（或将运输独立为固定物流配置区，而非可拖动普通环节）；非法修改应在保存前阻止并说明原因。按用户允许修改流程的要求，其他普通工序仍可调整。

**X09：删除画稿遗留悬空日志。**
- 复现：图集有某张画稿的 `pieceIds` 日志；从逐张画稿列表删除这张画稿；日志仍引用不存在的 ID。
- 根因：`delete-piece` 只删 `p.pieces[]` 并修改数量型步骤总量，没有处理日志引用。
- 方案：优先采用软删除画稿、保留其历史；若真的永久删除，先列出影响，关联日志一起调整或记录明确的删除状态，保证引用完整。

### P1：流程反馈、历史追溯和数据校验

**X04：修改活动收货 DDL 未提示影响范围。** 目前 `save-event` 直接更新 `e.ddl` 并重算所有关联制品，未展示变动的最晚寄出、印厂生产和约稿节点。应先出现变更预览及“确认调整”，历史事实及原基线不覆盖。

**X05：已验收外部交稿节点从日历消失。** `organizerNodes()` 使用 `if(!row.end||row.complete)continue`，完成后不再生成蓝色历史节点。应明确区分“仍待关注”与“已完成历史”，当前日期可灰显、历史日期可以查询真实完成日，避免重新催稿。

**X06：未来实际进度无拦截。** 个人记录日期可填未来十天，`save-log` 将其作为已发生记录直接存储。建议限制实际记录不晚于今天；若未来需要规划，只作为独立计划输入。用户尚未专门确认这一具体限制，因此此项是**数据有效性设计建议**，不是现有代码语法错误。

**X10：在进度表单取消完成勾选没有作用。** `save-log` 只有 `if (v.complete)` 分支，没有处理取消勾选；用户可以在“管理流程”恢复，但日志表单表现为可取消。应让复选框同步支持撤销并保留审计历史，或明确只读并引导至实际恢复入口。

**X11：在编辑工序时取消“已完成”，`completedAt` 仍是原日期。** `saveStepModal()` 改 `s.completed`，但没有同步清理/归档 `s.completedAt`。应以状态变更事件保持一致，恢复后当前有效完成日为空，旧完成事实仍作为历史事件保存（如需）。

**B18：实际新增量可大幅超出预估目标，且没有提示。** 测试中总目标 5000 字仍可记录 99999 字。小说真实字数可能合理地超出**预估**，不应该简单禁止超额；正确做法是提示“已超过原目标，是否更新预计总量”，并确保数量守恒与阶段完成状态一致。此项属于**交互校验不足**，不是必须阻止的输入。

### P2：清理性问题（影响维护体验，但不一定立即使排程错误）

**X02：删除制品后留下孤立原计划基线。** `delete-product` 删制品和日志，但未删除/归档 `data.baselines[p.id]`。建议同时清理或移入明确的历史归档，不再作为活动数据的一部分。

**U01：制品间管理模式串扰。** `ui.manageProduction` 是全局布尔值，`select-product` 只重置 `expandedTracks`；用户在制品 A 打开管理功能，切换 B 仍是管理状态。建议按制品 ID 保存展开状态或切换时重置。

**U02：本人工作还显示“提前提醒”。** 制品中本人工作内容也生成“提醒”按钮，但 `organizerNodes()` 不包含本人任务，修改它并不会产生对应的黄色催稿节点。建议本人工作只保留每日进度/个人截止日期，催稿提醒设置只出现在外部节点/下印等有效位置。

**U03：仍有遗留技术代码。** 公开 HTML 虽不显示旧版迁移入口，但打包了 `FandomLegacyAdapterP0.migratePreview` 等只读适配函数及 `select-day` 无 UI 入口分支。旧版数据迁移已被明确取消；后续重构可将其移出正式单文件以减轻维护负担，不应误称有可用迁移功能。

## 7. 预计的修复顺序及每项验收

| 修复批次 | 内容 | 最低验收 |
|---|---|---|
| **V0.8-P0A** | 今日任务不再受过期倒排日期直接过滤 | 即使 DDL 昨天已过，只要有未完成本人任务，“我的进度”必须显示它并明确逾期，不伪造合理配额 |

## 8. 未完成、不可断言的范围

- 未在真实手机设备、Safari、Firefox、不同系统时区/DST、数千条以上日志、长时间运行/浏览器存储上限下做全面测试。
- 对“工作日/自然日”“官仓每天几点截收”“不同快递揽收时段”没有外部物流数据，此站当前仅按本地自然日计算，不保证真实物流时效。
- 一天多制品能同时列任务，但尚无个人每日可用工时上限或智能资源冲突优化；**不能声称系统已证明安排可执行**。用户并未要求复杂资源计划软件，只需诚实显示任务汇总和超期警告即可。
- `JSON` 只支持导出，若清缓存无法用界面回导。这是**当前能力限制**，不等于用户同意加旧版迁移。
- 这 54 项是代表性单一与交叉路径测试，并非 61 个 UI 分发分支的每个参数组合都通过、也不是形式化代码覆盖率。
